# 2026-08-25 학습 일지

## 주제

수동 Git 작업 능력 회복: worktree 분리부터 Pull Request 병합과 브랜치 정리까지

## 수행한 작업

1. `main`을 기본 worktree에 유지하고 `docs/manual-git-recovery` 브랜치를 별도 worktree에 연결했다.
2. 변경 파일을 확인한 뒤 `git diff --check`, 구조 검사, ESLint, Prettier 검사를 실행했다.
3. `git add .`로 변경을 스테이징하고 `git diff --staged --stat`과 `git diff --staged`로 커밋 대상을 검토했다.
4. Git 작성자 설정을 확인하고 문서 변경을 로컬 커밋으로 만들었다.
5. `git push -u origin docs/manual-git-recovery`로 upstream을 설정하면서 작업 브랜치를 게시했다.
6. `main`을 base로, 작업 브랜치를 head로 지정해 PR을 만들고 CI 통과를 확인한 뒤 squash merge했다.
7. `fetch` 후 로컬 `main`과 `origin/main`의 차이를 확인하고 fast-forward로 동기화했다.
8. 별도 worktree와 로컬 작업 브랜치를 제거하고 원격 작업 브랜치도 삭제했다.

## 실패한 지점과 원인

- worktree를 저장소 내부의 `worktrees/`에 만들자 부모 저장소에서 해당 폴더가 추적되지 않은 파일로 나타났다. worktree 경로는 저장소 밖의 `/tmp`로 옮겼다.
- `npm eslint`와 `npm prettier`는 npm 자체 명령이 아니어서 실패했다. 로컬 패키지 실행에는 `npx eslint`와 `npx prettier`를 사용했다.
- `git config get name`은 설정 키에 섹션이 없어서 실패했다. Git 설정 키는 `user.name`처럼 `섹션.이름` 형식으로 지정한다.
- `git merge ff-only origin`은 `ff-only`를 병합 대상으로 해석해서 실패했다. 옵션은 `--ff-only`로 쓰고, 병합 대상은 `origin/main`처럼 별도로 지정한다.
- 원격 브랜치를 삭제할 때 `origin/docs/manual-git-recovery`를 전달하자 실제 원격 ref를 찾지 못했다. `origin`은 원격 저장소 인수로 한 번만 쓰고 브랜치 인수에는 `docs/manual-git-recovery`만 지정한다.

## 확인한 개념

- worktree는 작업 폴더이고 브랜치는 커밋을 가리키는 포인터다. 한 브랜치는 동시에 하나의 worktree에서만 체크아웃할 수 있다.
- `git diff --staged --stat`은 스테이징된 변경량을 요약하고, `git diff --staged`는 스테이징된 전체 내용을 보여준다.
- `origin`은 원격 저장소 URL에 붙인 로컬 별칭이며 `-u` 또는 `--set-upstream`은 로컬 브랜치의 기본 push와 pull 대상을 설정한다.
- PR의 base는 변경을 받을 브랜치이고 head는 변경을 제공하는 브랜치다.
- `fetch`는 `origin/main` 같은 원격 추적 브랜치를 갱신하지만 현재 로컬 브랜치는 움직이지 않는다.
- `git merge --ff-only origin/main`은 현재 브랜치를 `origin/main`까지 직선으로 이동할 수 있을 때만 동기화한다.
- squash merge는 작업 브랜치의 커밋과 다른 해시의 새 커밋을 `main`에 만든다. 따라서 Git이 작업 브랜치 커밋을 현재 `HEAD`에 병합된 것으로 판단하지 못할 수 있다.
- `origin/docs/manual-git-recovery`는 로컬의 원격 추적 브랜치 이름이고 GitHub의 실제 브랜치 이름은 `docs/manual-git-recovery`다.
- 짧은 옵션은 보통 `-u`처럼 하이픈 하나와 한 글자를 쓰고 긴 옵션은 `--set-upstream`처럼 하이픈 두 개와 단어를 쓴다. 정확한 지원 형태는 각 명령의 `--help`에서 확인한다.
