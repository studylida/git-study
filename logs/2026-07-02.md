# 2026-07-02 학습 일지

## 주제

실전 운용: 다중 기기 GitHub 동기화 루틴

## 학습 내용

### 노트북/본체 작업 루틴

- 작업 시작 전에는 `pull --ff-only`로 원격 변경을 먼저 가져온다.
- 작업 종료 전에는 `status -sb`로 변경된 저장소를 확인한다.
- 변경된 저장소별로 `add → commit → push` 순서로 마무리한다.
- 여러 저장소는 `for` 루프와 `git -C`로 한 번에 점검할 수 있다.

### 실제 정리한 저장소

`study` 폴더를 `studylida` 계정 기준으로 정리했다.

```text
2026-01
database-study
git-study
linux-study
regex-study
```

- `linux-study`, `git-study`, `2026-01`은 `studylida` 원격으로 전환 후 push했다.
- `regex-study`는 `studylida/regex-study` private 저장소를 새로 만들고 push했다.
- `database-study`는 새로 가져와 `study`의 submodule로 추가했다.
- `2026-01`의 zip 파일은 Git LFS로 추적했다.

## 실습 명령어

시작 루틴:

```bash
cd /mnt/c/git/study

for d in 2026-01 database-study git-study linux-study regex-study; do
  echo "===== $d ====="
  git -C "$d" pull --ff-only
done
```

종료 전 확인:

```bash
cd /mnt/c/git/study

for d in 2026-01 database-study git-study linux-study regex-study; do
  echo "===== $d ====="
  git -C "$d" status -sb
done
```

변경 저장소 마무리:

```bash
git add -A
git commit -m "docs: update notes"
git push
```

## 기억할 점

- `pull --ff-only`가 실패하면 로컬과 원격이 갈라진 것이다.
- `ahead`는 push할 커밋이 있다는 뜻이고, `behind`는 pull할 커밋이 있다는 뜻이다.
- submodule은 하위 저장소를 push한 뒤, 필요하면 부모 저장소에서 포인터 변경도 커밋해야 한다.
- LFS 파일은 push 중 `Uploading LFS objects` 출력으로 업로드 여부를 확인할 수 있다.

## 추가 실습: WSL 환경에서 parent/submodule 시작 루틴 점검

### 확인한 내용

- WSL에서 `~/code`가 parent 저장소 `studylida/study`임을 확인했다.
- `~/code/git-study`는 parent가 아니라 submodule 저장소 `studylida/git-study`임을 확인했다.
- `ssh -T git@github.com`으로 GitHub SSH 인증이 성공하는지 확인했다.
- parent 저장소에서 `git fetch origin`과 `git pull --ff-only origin main`으로 최신 상태를 확인했다.
- `git submodule sync --recursive`로 `.gitmodules` 기준 submodule URL 설정을 로컬 Git 설정에 반영했다.
- `git submodule update --init --recursive`로 parent가 기록한 submodule 커밋에 맞췄다.
- `git submodule status`의 공백, `+`, `-`, `U` 의미를 정리했다.
- `git submodule update` 후 submodule이 `HEAD (no branch)`가 될 수 있고, 작업하려면 `git switch main`이 필요하다는 점을 확인했다.
- `git lfs status`와 `git submodule foreach 'git lfs status'`로 LFS 변경사항이 없는지 확인했다.

### 오늘 정리한 판단 기준

작업 시작 가능 상태는 parent와 작업할 submodule이 모두 `main...origin/main`이고, 변경사항 표시가 없으며, LFS 대기 항목이 없는 상태다.

submodule에서 작업한 뒤에는 해당 submodule에서 먼저 `commit → push`를 하고, parent 저장소에서 submodule 포인터 변경이 생겼는지 확인한다.

## 추가 실습: PR 기반 종료 루틴

### `git-study` 변경 PR

- `git-study`에서 다중 기기 동기화 루틴 노트, 오늘 로그, review 용어를 수정했다.
- 처음에는 `main`에서 커밋한 뒤 작업 브랜치를 만들었다.
- 이후 `docs/multi-device-sync-routine` 브랜치를 GitHub에 push하고 PR을 만들었다.
- PR은 squash merge로 병합했고, 원격 작업 브랜치는 삭제했다.
- squash merge 후 로컬 `main`의 원래 커밋과 GitHub `main`의 squash 커밋이 갈라질 수 있음을 확인했다.
- `git log --oneline --graph --decorate --left-right main...origin/main`으로 양쪽 커밋을 비교했다.
- `git diff --stat main origin/main`으로 최종 파일 내용이 같은지 확인했다.
- working tree와 staging area가 깨끗한지 확인한 뒤, 로컬 `main`을 `origin/main`에 맞춰 정리했다.

### parent `study` submodule 포인터 PR

- `git-study` PR이 merge된 뒤 parent `study`에서 `M git-study`가 보였다.
- 이것은 parent가 기록하는 `git-study` submodule 포인터가 바뀌었다는 뜻이다.
- `git diff --submodule`로 `git-study`가 이전 커밋에서 새 squash merge 커밋으로 이동한 것을 확인했다.
- parent 저장소에서도 `chore/update-git-study-submodule` 브랜치를 만들고 submodule 포인터 변경을 커밋했다.
- parent PR도 squash merge했고, 원격/로컬 작업 브랜치를 삭제했다.
- parent에서도 squash merge 후 로컬 `main`과 `origin/main`이 갈라졌고, diff가 비어 있음을 확인한 뒤 정리했다.

### 오늘의 교훈

- 회사식 작업에서는 `main`에서 바로 커밋하지 말고, 작업 전에 브랜치를 먼저 만든다.
- 커밋 후 브랜치를 만들어도 되지만, squash merge 후 로컬 `main` 정리가 번거로워진다.
- PR merge 후 작업 브랜치는 삭제한다.
- submodule 작업은 하위 저장소 PR과 parent 포인터 PR이 별도 단계다.
- `reset --hard`는 루틴 명령이 아니라, diff와 status로 안전을 확인한 뒤 사용하는 정리 명령이다.
